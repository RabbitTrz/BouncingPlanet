先看这三句话：

  2. 每天开始工作先“拉取”，结束工作要“提交 + 推送”。
  3. 不要删除 .git，不要强制推送，不要改别人的文件；遇到红色报错先停手，

一、几个名词（30 秒看懂）
======================================================================
仓库（Repository / Repo）
  这个项目的全部文件和历史记录，就是本地的 BouncingPlanet 文件夹（里面藏着一个
  .git 文件夹，不要动它）。

远程仓库（Remote / Origin）
  GitHub 上的那一份。本地和云端通过“拉取 / 推送”同步。

克隆（Clone）
  第一次把 GitHub 上的仓库完整下载到本地。只做一次。
  不要用网页上的 “Download ZIP”，那只是快照，不能同步，也可能缺 Git LFS 文件。

拉取（Pull）
  把云端最新的改动下载到本地。每天开工前做。
  重要：拉取前先关闭 Unity，避免文件被占用。

提交（Commit）
  把你在本地改的文件打一个“存档点”，并写一句说明。提交只发生在本地。

推送（Push）
  把本地的存档点上传到 GitHub。提交后必须推送，别人才能看到。

分支（Branch）
  并行的开发线。团队约定日常都用 main 分支；如果你看到当前分支不是 main，
  先问程序，不要直接把东西提交到陌生分支。

冲突（Conflict）
  两个人改了同一行/同一个文件，Git 不知道该保留谁的。遇到冲突不要乱选，
  截图发群里让程序处理。

Git LFS
  大文件存储。图片、PSD、音频、模型等会自动存到 LFS，GitHub 仓库里只留指针。
  策划和美术也需要安装 Git LFS，否则同步到的可能只是 1KB 的“指针文件”。

.meta 文件
  Unity 为每个资源/文件夹生成的身份证（记录 GUID）。必须和资源一起提交，
  永远不要删除、不要手工改。否则 Unity 会丢引用（材质变粉、脚本丢失）。

二、一次性准备（只做一次）
======================================================================
2.1 安装软件
----------------------------------------------------------------------
1) GitHub Desktop（推荐所有人使用，图形界面，不用敲命令）
   下载：https://desktop.github.com/
   安装后打开，用你的 GitHub 账号登录。

2) Git for Windows（GitHub Desktop 可能会提示安装）
   下载：https://git-scm.com/download/win
   安装时一路默认即可。

3) Git LFS（必须）
   下载：https://git-lfs.com/
   安装后打开一次终端（PowerShell 或 Git Bash），运行：
       git lfs install
   看到 “Git LFS initialized” 即可。
   验证：
       git --version
       git lfs version
   两条都能显示版本号才算装好。

4) Unity Hub 和 Unity 2022.3.62f3c1
   用 Unity Hub 安装与项目完全一致的版本。
   打开项目时如果提示升级版本，选择“不升级 / 使用当前版本”，
   升级 Unity 会产生大量文件变化，必须先和程序确认。

2.2 让管理员把你加入仓库
----------------------------------------------------------------------
本仓库是公开仓库：任何人都能看，但只有被邀请的人能推送。
把你的 GitHub 用户名发给管理员，管理员会在：
  GitHub 仓库 → Settings → Collaborators → Add people → 选择 Write 权限
邀请你。去邮箱/GitHub 通知里接受邀请。
没有接受邀请或没有 Write 权限时，推送会失败。

2.3 克隆仓库（第一次下载）
----------------------------------------------------------------------
推荐用 GitHub Desktop：
  1) 打开 GitHub Desktop → File → Clone repository
  2) 选择 URL 标签页，粘贴管理员发的仓库地址
  3) Local path 选择本地目录，例如：
         D:\GameJam\BouncingPlanet
     不要放在 OneDrive、坚果云、百度网盘等自动同步目录里，
     云盘和 Git 同时同步同一个文件夹容易把 .git 弄坏。
     路径尽量使用英文，避免空格和特殊符号。
  4) 点击 Clone。
  5) 等待下载完成；启用了 Git LFS 的图片/音频会一起下载。

如果你已经用“Download ZIP”下载过：删掉那个文件夹，重新按上面步骤克隆。
ZIP 不能拉取/推送，也会缺 .meta 或 LFS 文件。

2.4 用 Unity 打开
----------------------------------------------------------------------
  Unity Hub → Add → 选择克隆下来的 BouncingPlanet 文件夹 → 用
  2022.3.62f3c1 打开。
  第一次打开会重新生成 Library，需要等一会儿；Library 不在仓库里是正常的，
  不要把它提交上去。

2.5 你该在哪个目录工作
----------------------------------------------------------------------
当前约定（后续如有调整以群公告为准）：
  美术图片：Assets/Resources/Image/
  音频：    Assets/Resources/Audio/
  策划配置：Assets/Config/（只改指定给你的资产，不要动别人的）
  程序：    Assets/Scripts/、Assets/Scenes/、Assets/Prefabs/、
            ProjectSettings/、Packages/
不要新建顶层目录、不要改目录结构；需要调整先问程序。
所有资源请使用英文/拼音文件名，不要用中文、空格和特殊符号，
避免 Windows / macOS / Git 之间出现编码和路径问题。

三、每天的标准流程（最重要）
======================================================================
3.1 开始工作：先拉取
----------------------------------------------------------------------
  1) 保存并关闭 Unity（File → Save，然后退出 Unity）。
     如果 Unity 开着，某些文件会被锁住，拉取可能失败或损坏资源。
  2) 打开 GitHub Desktop，确认右上角 Current Branch 是 main。
  3) 点击 Fetch origin，再点击 Pull origin（如果有更新）。
  4) 重新打开 Unity，等右下角导入/编译完成再开始改东西。
  5) 如果拉取后 Unity 提示“缺失脚本 / 材质变粉”，先等它重新导入；
     仍然不对就截图发群里，不要自己删文件。

3.2 工作中
----------------------------------------------------------------------
  - 只改自己负责的文件/目录。
  - 使用 Unity 内部来创建、移动、重命名资源（这样 .meta 会跟着走）。
  - 经常保存（Ctrl+S）。不要在 Unity 正在导入或编译时提交。
  - 不要同时用两台电脑/两个 Unity 实例打开同一个工程目录。
  - 不要直接改 ProjectSettings、Packages、.gitignore、.gitattributes。

3.3 结束工作：提交 + 推送
----------------------------------------------------------------------
  1) 保存所有文件，等 Unity 导入/编译完成，然后关闭 Unity。
  2) 回到 GitHub Desktop，左侧 Changes 会列出改动。
  3) 逐个检查文件列表：
       - 只应有你本次改的文件；
       - 应该包含新资源对应的 .meta；
       - 不应该出现 Library、Temp、Logs、Builds、UserSettings、.vs、
         *.csproj、*.sln 等生成文件。
  4) 在左下角 Summary 写提交说明（格式见第四节），Description 可留空。
  5) 点击 Commit to main。
  6) 点击右上角 Push origin。
  7) 推送完成后，确认界面显示 “Last fetched just now” 或没有待推送的提交。

如果推送被拒绝（rejected）：
  说明云端有别人的新提交。先 Pull origin，再 Push。
  如果 Pull 后出现冲突（Conflict），停止操作，截图发群里让程序处理。
  绝对不要点 “Force push”。


======================================================================
四、同步规范（必须遵守）
======================================================================
4.1 文件所有权
----------------------------------------------------------------------
  - 美术只改自己的图片/模型资源；音频只改音频；策划只改编好的配置资产；
    程序负责代码、场景、预制体、工程设置。
  - 不经过允许，不要改别人的资源、目录名、文件名。
  - 需要改公共资源（共用材质、共用预制体）时，先在群里说明并约定时间。

4.2 场景（Scene）和预制体（Prefab）
----------------------------------------------------------------------
  - 同一个场景/预制体同一时间只能有一个人编辑。
    开始编辑前在群里说一句“我改 Main 场景，10 分钟后提交”，改完尽快提交。
  - 场景冲突很难手工解决，程序也可能需要重做。不要两个人同时改。
  - 美术尽量以“独立贴图/独立预制体”交付，不要把大量改动塞进公共场景。

4.3 .meta 文件
----------------------------------------------------------------------
  - 新增资源时 Unity 会生成同名 .meta，必须一起提交。
  - 不要删除 .meta，不要手工编辑 .meta，不要把 .meta 排除在提交之外。
  - 移动/重命名资源请在 Unity 里做，让 Unity 自动处理 .meta。
  - 如果看到没有对应资源的 .meta，先问程序，不要直接删。

4.4 绝对不要提交的内容
----------------------------------------------------------------------
  下面这些都已在 .gitignore 中忽略，正常情况下不会出现在 Changes 里：
    Library/、Temp/、Logs/、UserSettings/、Builds/、.vs/
    *.csproj、*.sln、*.user、*.pidb
    *.apk、*.aab、*.app、*.unitypackage
  如果它们出现在 Changes 里，不要勾选提交，截图告诉程序。

4.5 文件命名
----------------------------------------------------------------------
  - 资源文件和文件夹用英文/拼音，不用中文、空格、#、? 等特殊字符。
  - 使用有意义的名称，例如：
        rock_body_01.png
        sfx_bounce_metal_01.wav
        planet_ice_crack_02.png
  - 同一类资源保持统一前缀；版本号用 _01、_02。
  - 游戏里显示的中文名称不受此限制。

4.6 提交说明格式
----------------------------------------------------------------------
  格式：
      [角色] 一句话说明

  角色前缀：
      [美术]   图片、模型、动画资源
      [音频]   音乐、音效
      [策划]   数值、配置、文档性配置
      [程序]   代码、场景、预制体、工程设置
      [配置]   仅 ScriptableObject / 数据资产
      [修复]   修 bug
      [同步]   合并、目录整理等

  示例：
      [美术] 新增果冻星基础贴图和受伤闪白图
      [美术] 调整岩石星贴图尺寸
      [音频] 加入普通撞击音效第一版
      [策划] 调整冰星反弹系数
      [程序] 实现钩锁断开判定
      [修复] 修正相机左右方向镜像

  一次提交只做一件事。不要写 “update”“改了一下” 这种说明。
  不要把无关文件混进同一个提交。

4.7 分支
----------------------------------------------------------------------
  - 日常统一在 main 分支工作；小步提交、频繁推送。
  - 程序如果创建了 feature/xxx 分支，策划和美术不要切过去提交，
    除非程序明确说可以。
  - 永远不要强制推送（Force push），不要修改历史提交。
  - 不要在 GitHub 网页上直接 “Upload files” 上传 Unity 资源：
    容易丢 .meta、绕过 LFS、造成目录错乱。统一用 GitHub Desktop。

4.8 冲突处理
----------------------------------------------------------------------
  - GitHub Desktop 提示 Conflict / “Please resolve conflicts” 时：
      1) 停手，不要再点任何按钮；
      2) 截图；
      3) 在群里 @程序负责人；
      4) 等程序处理完再继续。
  - 场景/预制体冲突不要手工编辑 .unity / .prefab 文件；
    普通文本冲突也交给程序判断，避免误删别人的改动。
  - 看到 “merge in progress”“rebase in progress”“detached HEAD” 等状态，
    一律停下来问程序。

4.9 公开仓库注意事项（本项目是 Public）
----------------------------------------------------------------------
  - 所有人都能看到代码、资源和历史记录。不要上传：
      个人隐私、聊天记录、合同、联系方式、密码/Token、
      未获授权的付费素材、限制再分发的字体/音乐/插件。
  - 使用第三方素材前确认许可证允许公开分发，并在群里登记来源。
  - 提交记录会显示提交者邮箱；管理员应使用 GitHub 的 noreply 邮箱或专用邮箱。
  - 公开不等于可以随便改：只有被邀请的 Collaborator 能推送。
  - 不要在仓库里放构建产物、大视频、录屏原文件；需要分享用网盘。

4.10 Unity 相关
----------------------------------------------------------------------
  - 不要升级 Unity 版本；不要改 ProjectSettings / Packages（程序除外）。
  - 拉取前关闭 Unity；拉取后重新打开并等待导入完成。
  - Unity 导入过程中不要提交。
  - 新建资源后确认 .meta 已生成再提交。
  - 如果资源在 Unity 里显示丢失/粉色：先 Refresh/重新导入，再问程序。
  - 不要删除 Library 后强行提交；Library 是本地缓存，删了重新打开会生成。

4.11 大文件与 Git LFS
----------------------------------------------------------------------
  - 图片、PSD/PSB、Krita/Clip、音频、FBX/Blend、视频、字体、插件等
    已配置为自动走 LFS，正常提交即可。
  - 不要修改 .gitattributes 里的 LFS 规则，除非你是程序且确认过。
  - 单个文件特别大（例如 >100MB 的视频/分层源文件）先问程序，
    不要直接塞进仓库；GitHub LFS 有免费额度，超额会推送失败。
  - 如果克隆后发现 PNG 打不开、文件只有约 1KB，说明拿到的是 LFS 指针：
      安装 Git LFS 后，在仓库目录运行：
          git lfs install
          git lfs pull
    或者让 GitHub Desktop 重新拉取。
  - 不要用 “Download ZIP” 获取项目，否则 LFS 大文件可能缺失。

五、常见问题（照着做，不要慌）
======================================================================
Q1. 打开 GitHub Desktop，Changes 里有几千个 Library 文件怎么办？
  → 不要提交。说明 .gitignore 被绕过或有人强制添加了。
    截图给程序。绝对不要点 Commit。

Q2. 点 Push 提示 rejected / failed to push 怎么办？
  → 先 Pull origin，再 Push origin。
    如果 Pull 出现冲突，停手，截图，找程序。不要 Force push。

Q3. Pull 提示 “You have uncommitted changes” 怎么办？
  → 你本地还有没提交的改动。先判断：这些改动是不是你本次要保留的？
    - 是：先按规范提交（Commit），再 Pull；
    - 不确定：不要点 Discard，截图问程序。
    Discard changes 会永久删除本地修改。

Q4. 不小心提交了 Library / 大文件 / 密码怎么办？
  → 立刻在群里告诉程序，不要自己删历史或强推。
    已经推到公开仓库的内容可能已被别人看到，删除也不能保证彻底消失。

Q5. 克隆后图片是白色/打不开/只有 1KB？
  → 大概率是 Git LFS 没装或没拉取。按 4.11 操作。

Q6. Unity 打开提示版本不一致 / 要升级项目怎么办？
  → 取消升级，安装 2022.3.62f3c1。升级前必须问程序。

Q7. Unity 里资源丢失、材质变粉、脚本 Missing 怎么办？
  → 等 Unity 重新导入；检查是否漏提交 .meta；确认分支/版本正确；
    仍不行就截图给程序，不要删 Library 或资源。

Q8. 我改错了，想回到上次提交的版本？
  → 在 GitHub Desktop 的 History 里查看，但不要自己点 Revert/Undo。
    先问程序，避免把别人的改动一起回滚。

Q9. 我和别人都改了同一个文件，GitHub Desktop 变红/提示冲突？
  → 不要手工解决。停止，截图，交给程序。

Q10. 我可以直接删除 .git 文件夹重新克隆吗？
  → 不可以。那会丢失本地历史和未推送的提交。先问程序。

Q11. 我可以在 GitHub 网页上直接上传图片/改文件吗？
  → 不推荐。Unity 资源必须带 .meta，网页上传容易漏；大文件也可能绕过 LFS。
    统一用 GitHub Desktop。

Q12. 推送成功但别人看不到我的文件？
  → 确认你点的是 Push origin，不是只 Commit；确认分支是 main；
    让对方先关闭 Unity 再 Pull。

Q13. 我可以同时开两个 Unity 打开同一个项目吗？
  → 不要。文件锁和导入会互相干扰。用不同副本也要先问程序。

Q14. 我只需要最新文件，可以下载 ZIP 吗？
  → 不要用于工作。用 Clone / Pull；ZIP 不能同步，也可能缺 LFS 和 .meta。

七、管理员 / 程序附录
======================================================================
7.1 创建仓库（管理员）
----------------------------------------------------------------------
  1) 在 GitHub 新建 Public 仓库，例如 BouncingPlanet。
  2) 不要勾选 “Add a README file”“Add .gitignore”“Choose a license”，
     保持空仓库，避免和本地首次推送冲突。
  3) 把仓库地址发给程序，由程序执行：
         git remote add origin <仓库地址>
         git push -u origin main
  4) 添加成员：
         Settings → Collaborators → Add people → 选择 Write 权限
     让对方接受邀请。
  5) 不建议开启强制 PR 流程（会阻碍非技术成员）；但应禁止 force push，
     并约定 main 保持随时可打开。

7.2 程序常用命令（仅供参考）
----------------------------------------------------------------------
  git clone <仓库地址>
  cd BouncingPlanet
  git lfs install
  git lfs pull

  git status
  git pull --rebase
  git add <具体文件或目录>
  git commit -m "[程序] 说明"
  git push

  不要使用：
    git push --force
    git reset --hard（除非你清楚会丢失什么，并且已确认）
    git add -A / git add .（容易误提交；请按目录/文件添加）
  修改历史、清理大文件、解决场景冲突，先和团队确认。

7.3 常见需要程序处理的情况
----------------------------------------------------------------------
  - 场景/预制体冲突
  - .gitignore 失效、Library 被误提交
  - LFS 指针异常、LFS 配额不足
  - 提交了密钥/大文件，需要清理历史
  - Unity 版本升级、Packages/ProjectSettings 冲突
  - 分支处于 merge/rebase/detached 状态

7.4 公开仓库合规提醒
----------------------------------------------------------------------
  - 所有第三方素材必须确认许可证允许公开分发。
  - 建议在仓库根目录维护 CREDITS.txt，记录素材来源、作者、许可证。
  - 提交邮箱建议使用 GitHub noreply 地址，避免公开个人邮箱。
  - 如项目未来要闭源或商业化，需提前评估公开历史中的素材授权。

八、遇到问题的处理顺序
======================================================================
  1. 停止操作，不要点 Discard / Force push / 删除文件。
  2. 截图（包含报错文字和 GitHub Desktop 界面）。
  3. 在群里说明：你做了什么、看到什么、希望达到什么。
  4. 等程序确认后再操作。
  5. 如果是 Unity 资源问题，保留现场，不要反复重开/删除 Library。

记住：Git 不可怕，绝大多数误操作都能救；真正危险的是“随手删 .git、
强制推送、批量 Discard、手工合并场景”。避免这四个动作，就不会出大问题。
